# FND-003 环境隔离与交付说明

## 这条需求是什么意思

原文：平台必须支持一个 DayPop Shared Integration 环境，以及每项目独立 Staging 和 Production 环境。

这里的 DayPop 是需求文档中的运营方名称。可以这样理解：工程师先在公共测试场地联调新功能，再到某个交付项目的预发布环境测试，确认后才部署到该项目的正式环境。客户和客服平时使用正式环境。

| 环境 | 谁使用、做什么 | 数据要求 |
| --- | --- | --- |
| 公共联调（Shared Integration） | 工程师联调邮件、接口、机器人等功能 | 一套公共环境，使用测试资料 |
| 项目 A 预发布（Staging） | 工程师和验收人员测试项目 A 的配置与版本 | 与 A 正式环境分开 |
| 项目 A 正式（Production） | 客户、客服、工程师处理真实业务 | 保存 A 的正式业务数据 |
| 项目 B 预发布、正式 | 分别测试和运行项目 B | 另建两套，不能共用 A 的业务数据库 |

这里的“交付项目”是需要独立部署和验收的一套服务，例如“知识管理服务交付”。它需要单独的部署编号，不是新建工单表单中的服务分类，也不是 FND-002 配置中 `projects[]` 的分类编号。

现有多租户能力继续保留。多租户解决不同公司在业务上的隔离；本需求进一步解决“测试版和正式版不能使用同一套业务存储”的问题。独立环境可以放在不同服务器，也可以在资源足够的同一台服务器上使用独立容器、网络、端口和目录；同一服务器仍存在主机故障和资源竞争的共同影响。

## 本次补齐的功能

| 补齐内容 | 对你有什么用 |
| --- | --- |
| 环境清单 | 明确哪一套是公共联调，哪些属于哪个交付项目，并要求每个项目同时列出预发布和正式环境 |
| 独立部署文件 | 每套分别生成数据库、缓存、文件存储等凭据，以及独立网络、镜像名、端口、数据和备份目录 |
| 部署前检查 | 检查同一服务器上的端口和目录冲突，检查网址、公司编号、环境和配置包是否一致 |
| 数据库身份绑定 | 数据库记录自己属于哪个项目、环境和公司；选错库、改错环境或移除身份参数时，启动和迁移会被拒绝 |
| 首次初始化 | 通过明确的初始化命令创建缺失的目标公司并应用初始配置；已有公司不会被覆盖或改名 |
| 操作入口 | 操作时必须选定实例和清单中的主机编号，并核对实际目录；不会因为继承了其他环境的变量而切到别的实例 |
| 备份与恢复保护 | 备份记录所属实例；恢复、恢复演练和回滚先核对身份，避免拿错环境的备份或回滚记录 |

数据库身份绑定和配置应用在同一个事务中完成：配置失败不会单独留下一个“已经绑定成功”的假状态。普通启动负责核对，首次创建公司和绑定由显式初始化执行。

旧数据库还没有身份记录时，也会检查已有的生效配置：不能把已有正式配置的库直接当成预发布库；一个旧库里有多个公司的生效配置时，需要先完成数据拆分和迁移，再接管为独立实例。

本轮交叉检查还修复了运营配置应用的权限检查位置，确保只有工单处理权限的客服不能应用管理员的运营配置草稿。沿用现有角色权限，没有新增身份体系。

## 工程师如何准备环境

### 1. 准备一份真实清单

参考 `deploy/environments/inventory.example.json`，在本地未跟踪目录（例如 `.local/environments/`）准备自己的清单。替换示例主机编号、网址、目录和公司编号；示例并不是已经存在的服务器。

本轮清单采用明确的公司映射：每个交付项目使用一个独立公司编号，同项目的预发布和正式环境使用同一编号，但各自有独立数据库；公共联调另用测试公司编号。已有公司填写真实编号；全新数据库可在显式初始化时创建该编号。该编号不能直接拿工单服务分类编号代替。

`config_bundle`：已有目标环境的 FND-002 导出包时填写文件路径；首次准备可以留空。留空会明确显示“待配置”，不会伪造配置版本或通过部署检查。

在仓库根目录执行（Windows 使用 `python`，Linux 可使用 `python3`）：

```sh
python scripts/environmentctl.py validate --inventory .local/environments/inventory.json
python scripts/environmentctl.py list --inventory .local/environments/inventory.json
python scripts/environmentctl.py render --inventory .local/environments/inventory.json --output .local/environments/packages
```

生成目录中包含密码和密钥，不能提交到 Git。生成器拒绝覆盖已有实例，因此重复运行不会悄悄重置密码。后续升级要保留原实例的凭据，不要用一套重新生成的密码替换现有数据库密码。

### 2. 本地核对，放到对应服务器

以下按示例“知识管理服务预发布”说明；正式环境和公共联调必须选择各自的实例、目录和主机编号。

```sh
python scripts/deploy-environment.py --package .local/environments/packages/onward-knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action check
```

`check` 只读取文件，不启动容器。将这一实例目录安全传输到清单约定的 Linux 目录 `/srv/onward/knowledge-service-staging`，并准备审核过的同版本代码、Docker Compose、HTTPS 反向代理和域名。

主机编号是清单中的运维标识，操作入口会检查它与所选实例相符；它不是自动发现服务器的功能。工程师仍需登录正确服务器。实际操作拒绝非本机 Docker 连接设置。

### 3. 准备公司配置和密钥

为每个环境分别准备 FND-002 配置。公司编号、`environment`、工作时间、渠道开关等填写该环境真实使用的内容；邮件、外部接口使用对应测试或正式凭据。

密钥文件放到 `project-secrets/<公司编号>/<环境>/`。不要把密码写进清单或配置 JSON。配置校验通过不等于真实邮件、第三方接口已经联调通过。

首次空环境使用原始配置文档初始化；已有数据库应使用在该数据库中准备的版本导出包。不能认为从另一套数据库复制过来的版本编号必然存在于当前数据库。

### 4. 首次初始化和安装

以下命令在**选定的 Linux 服务器**、仓库根目录执行。先从本次部署的代码构建校验工具，并在该实例 `.env` 中填写唯一的 `IMAGE_TAG`，固定依赖镜像版本。

```sh
go build -o dist/remotehelpdesk ./cmd/server
```

将原始配置放到该实例的 `project-config/initial.json`，核对其中公司编号和 `environment=staging`。可参考仓库的 `config/project-configuration.runtime.example.json` 填写真实配置；它是原始配置文档，和包含 `version_id/digest/document` 的部署导出包不同。

新公司还需要企业管理员。工程师先通过受控方式准备 `project-secrets/1001/staging/bootstrap-admin-password`（示例公司编号为 `1001`），文件权限为 `0600`，密码为 12–72 字节；不要将密码写进命令、清单或配置 JSON。文件仅供初始化读取，不需要作为运营设置中的 `secret_refs` 声明。以下命令创建 `knowledge.admin` 企业账号：

```sh
python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action initialize-config --document /srv/onward/knowledge-service-staging/project-config/initial.json --tenant-name '知识管理服务公司' --admin-username knowledge.admin --admin-password-file /srv/onward/knowledge-service-staging/project-secrets/1001/staging/bootstrap-admin-password

python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action preflight

python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action install

python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action doctor
```

初始化命令会先校验原始配置和主机条件，再构建 API、启动该实例的 PostgreSQL，将公司、管理员、权限、配置与部署身份一起提交，生成本库自己的 `current.json` 并同步 `.env` 中的摘要。之后 `install` 启动其余服务。初始化不会发送邮件，也不启动后台业务处理。

若已有尚未归属企业、客户或协作方的独立账号，可用 `--admin-user-id <账号编号>` 替代上述两个管理员参数。已有正常管理员的重复初始化可省略管理员参数；指定同一账号也不会重置密码，指定其他管理员会被拒绝。旧初始化已经创建公司但没有管理员时，可以保留完整 `current.json`，使用完全相同的配置和管理员参数重新执行初始化来补齐；文件内容或版本不匹配时不会覆盖。安装后用新企业账号登录，或通过平台“进入企业”检查权限。

普通 API 以非 root 用户读取文件。生成的非敏感 YAML 和配置目录允许读取；`.env` 和密钥保持私有。工程师应按 API 用户的实际 UID/GID 设置密钥目录的读取权限或 ACL。脚本会以普通 API 用户验证能否读取配置和实际引用的密钥，失败会明确停止，不会自动把密钥改成所有人可读。

若初始化已经生成 `current.json`，但文件权限检查或摘要同步中断，先修正提示的读取权限，再执行：

```sh
python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action sync-config-digest
```

若中断发生在设置 `current.json` 读取权限之前，可以只将该不含密码的文件改为 `0644`。不要删除数据库重来，也不要重新生成整套基础密码。`sync-config-digest` 只重新验证并同步摘要，不替换数据库生效配置。

如果进程被强制终止，导致 `current.json` 为空或只写了一半，应先将该未完成文件改名保存，再用完全相同的原始配置重新初始化。数据库已提交相同配置时会安全重试导出；内容不同会被拒绝，不会覆盖已有生效配置。

### 5. 后续升级、备份和检查

仍选择同一实例，把操作改为 `status`、`backup`、`restore-drill` 或 `upgrade`。升级沿用现有备份、恢复演练、配置应用和健康检查流程；如果同时修改业务配置，先按照 FND-002 流程在目标库准备并导出新版本。

```sh
python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action backup
python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action restore-drill
python3 scripts/deploy-environment.py --package /srv/onward/knowledge-service-staging --instance onward-knowledge-service-staging --host-id staging-host --action upgrade
```

备份的 `.dump`、`.sha256`、`.meta` 和 `.config.json` 必须一起保存。配置包来自备份时数据库正在使用的版本，即使磁盘已准备下一版本，也能正确备份。备份期间配置发生变化会失败，不会发布混合版本的备份。跨环境备份不能直接用于恢复。

恢复使用 `bash deploy/1panel/rhdctl --env-file <实例目录>/.env restore <备份.dump> --confirm <数据库名>`。恢复前会检查配套文件、公司与环境、摘要、历史密钥，以及普通 API 用户能否读取历史配置；随后创建安全备份，停止应用，恢复数据库和对应配置，更新 `.env` 摘要并启动检查。所选旧备份不会被本次安全备份的保留策略清理。数据库或配置恢复失败会保持应用停止，并保留安全备份。两个配置文件分别原子替换；若文件更新中断，应检查失败原因后恢复匹配文件或运行 `sync-config-digest`，不可绕过启动检查。

未包含配套配置的旧备份不会自动恢复到受管环境，需先由工程师核对并准备匹配的配置归档。真实密钥不随配置包备份，恢复时须保留对应的受控密钥。主机需要 Python 3 及当前版本的 Go 配置校验工具；仅含 PostgreSQL 的工具容器无法替代受管实例恢复入口。回滚应用镜像不会自动回滚数据库迁移，升级前仍需要核对迁移兼容性。

现有 `.github/workflows/deploy.yml` 和根目录 `docker-compose.prod.yml` 仍属于原来的单实例部署路线，**不能拿它们代替本次按实例部署入口**。本次未触发 CI、推送镜像或操作任何真实交付服务器。
