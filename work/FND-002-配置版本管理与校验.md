# FND-002 配置版本管理与校验

实现日期：2026-09-12。对应需求：所有项目差异由版本化 Project Configuration 表达，部署前通过 JSON Schema、Policy、Secret Reference 校验。

## 本次交付边界

在原有版本管理、三类校验、受理规则、工单追溯和部署检查基础上，配置契约 v2 已补入公司语言/时区/服务模式、工作日历、SLA 三类时限、渠道开关、SMTP 发信及重试、外部接入参数、现有数据保存策略和自动关闭设置。恢复历史 v2 内容会一起恢复这些设置。

当前交付口径是**现有 Go 多租户系统的运营配置功能及本地验收**。原文要求的 GLPI/Chatwoot 集成、独立项目实例以及真实生产部署并未由本次实现代替；不能据此宣称全 V1 投产或原文所有架构约束已验收。配置开关不会自动实现缺失的渠道适配器；密钥文件存在不证明第三方账号可连接。

数据保存设置接入现有日志、通知、隐私授权记录及审计清理任务；自动清理关闭或证据保留开启时，这些任务停止清理该公司。它不是 DAT-001/002 要求的全部工单、附件、指标、报表、备份分类保留与删除系统。数据区域只是设置标记，不会移动数据库所在地。SLA 仍兼容现有工单优先级编号，不代表 TKT-005 已完成。

## 页面使用

1. 打开企业工单 `/enterprise/tickets`，点击“新建工单”。
2. 点击受理渠道旁的“受理规则”齿轮。原受理规则需要已有 `ticket.update` 权限；运营配置另外要求现有公司所有者/管理员角色，或现有 `tenant.update` 权限。普通工程师不能因为可以修改工单就修改公司邮箱和保存策略。
3. 点击“载入现有运营设置（升级配置）”，生成待检查的 v2 草稿。核对公司设置、日历、时限、渠道、邮件、接入及保存策略；登记的服务项目是工单的服务分类，不是产品，也不是另一个租户。
4. 填写修改说明，点击“保存草稿”。此时原规则继续使用。
5. 点击“检查配置”。开发环境处理错误后点击“应用已检查的草稿”，后端再次校验。生产、预发布或绑定部署文件的环境显示“导出已检查的草稿”，由负责部署的工程师部署应用；页面和接口都不能直接改变生效版本。
6. 新建电话工单，详情显示受理及运营配置版本。资料不全仍可记录，并明确显示缺失内容。新工单 SLA 使用创建时版本，随后修改时限或日历不会改动其计时依据；转派时也保留该依据。
7. “历史与草稿”保留修改人、说明及应用记录；“载入为新草稿”用于恢复历史内容，必须另存、检查、应用。

新工单补充资料使用其记录的版本。旧工单标注“历史版本未记录”，按兼容方式读取有效规则，不伪造历史。首次保存草稿前会保存当时真实存在的旧规则作为迁移基线；更早被覆盖的内容无法还原。

迁移草稿会带入已有设置但不会导出密码。SMTP 和旧集成凭据需要工程师提供实际密钥文件；文件缺失时检查/应用失败。原无日历的 SLA 导入全天日历，避免把自然分钟偷偷改成工作日分钟；管理员可在草稿里改成工作日历。若现有同一公司存在多条保存策略，升级会要求先核对，不擅自丢弃其他策略。新版本中的空目标列表表示不为新工单配置 SLA；历史已绑定工单的原目标仍继续执行。

历史 v1 仅保存受理规则，不能还原当时尚未纳管的邮箱等设置。运营配置纳管后禁止直接降级成 v1；页面载入 v1 时保留当前运营设置，再另存为 v2。

## 数据与接口

- 三张表：`ProjectConfigurationVersion` 保存不可变内容，`ProjectConfigurationState` 指向有效版本，`ProjectConfigurationActivation` 保存每次应用记录。
- 公司与环境共同限定配置范围；版本中登记服务项目及其规则，不等于完成独立实例/数据库部署。
- 草稿以提交编号防重；相同编号不同内容或基于过期版本修改返回 HTTP 409。
- 草稿可以保留尚未填完的业务字段，但必须包含版本号和各列表；缺少列表或使用 null 会被拒绝。旧版空字段草稿仍可查看并载入新草稿，不改写原记录和摘要。
- 应用操作、兼容字段投影、应用记录及 Outbox 事件处于同一事务。失败全部回滚。
- 历史版本存 SHA-256；读取或部署时发现内容摘要不一致会失败。
- v2 生效后，旧邮箱、SLA/日历、保存策略、自动关闭、接入配置及公司受管字段写入口被阻止；相关写入与配置应用使用同一公司锁协调。旧页面仍可查看兼容数据；修改请使用配置草稿。
- GET `/api/enterprise/v1/ticket-settings/configuration`
- GET `/api/enterprise/v1/ticket-settings/configuration/upgrade`（生成迁移建议，不修改配置）
- POST `/api/enterprise/v1/ticket-settings/configuration/drafts`
- POST `/api/enterprise/v1/ticket-settings/configuration/validate`
- POST `/api/enterprise/v1/ticket-settings/configuration/:version/apply`
- GET `/api/enterprise/v1/ticket-settings/intake?ticket_id=123` 返回该工单绑定规则，并检查工单可见性。

## 配置校验和密钥

JSON Schema 定义在 `internal/pkg/projectconfig/schema.json` 并嵌入二进制。未知字段会被拒绝；当前不支持的设置不能通过增加任意 JSON 字段绕过校验。

v2 样例：`config/project-configuration.runtime.example.json`。包括有效时区、支持语言、工作日/假日、全天日历的 `00:00–24:00`、按服务分类和优先级指定的时限。时限必须引用已有日历，默认语言必须在支持语言列表中，受理规则使用的渠道必须启用。发信密码及应用凭据只允许密钥引用，连未应用草稿也不能保存密码。TLS 发信沿用现有隐式 TLS 连接，通常使用 465 端口；不要把 587 STARTTLS 当成同一种连接方式。

运行环境由 `RHD_PROJECT_ENVIRONMENT` 指定：`development`、`integration`、`staging`、`production`。本地未配置时为 development。改变此值会切换配置范围，不会迁移原环境的生效版本。

引用格式为 `secret://mail`。对应文件为：

`RHD_PROJECT_SECRET_DIR/<公司编号>/<环境>/mail`

引用只允许受控名称；拒绝路径穿越、子目录符号链接、非普通文件、空文件、超限文件以及跨公司/环境读取。目录和文件由运维管理，建议权限分别为 0700/0600。密码不写入配置版本或校验结果。既有 `secret://tenant-integration/...` 哈希标识不会被误认为可读取的真实密钥，需要显式配置。

## 首次部署及后续部署

构建校验/服务二进制：`go build -o dist/remotehelpdesk ./cmd/server`（Windows 可加 `.exe`）。不依赖宿主机安装另外一套 JSON 校验器。

已有环境从页面保存、检查并导出待部署草稿。部署时将其保存到 `deploy/1panel/project-config/current.json`，同步环境文件中的实际公司编号、环境和导出文件的 digest；示例见 `.env.example`。默认配置目录和密钥目录均不提交 Git。导出本身不改变正在使用的配置。

为已存在且已有管理员、尚无有效配置版本的目标公司初始化时，在能访问目标数据库的受控运维环境执行：

```bash
./remotehelpdesk -config config/config.yaml \
  -initialize-project-config config/project-configuration.example.json \
  -project-tenant 1 -project-environment development \
  -project-secret-dir /secure/project-secrets \
  -project-output /secure/project-config/current.json
```

运行前将样例中的公司编号、环境、服务规则改为目标配置。该命令是**明确的数据库写入操作**：执行迁移、初始化版本、记录系统操作，随后退出；不启动 Web 服务或消费者。上面的命令用于已有公司；新建公司及配置首个管理员的参数见 `work/FND-003-环境隔离与交付说明.md`。初始化不替换不同内容的已有生效配置；已存在且匹配的输出文件可安全复用，不匹配时拒绝覆盖。执行者需拥有目标数据库及密钥文件的本机权限。初始化成功但输出文件写入失败时可重试同一配置导出已有版本。

部署前只读校验：

```bash
./remotehelpdesk -check-project-config /secure/project-config/current.json \
  -project-tenant 1 -project-environment development \
  -project-digest <导出文件中的SHA256> -project-secret-dir /secure/project-secrets
```

1Panel 的严格 preflight（install/upgrade 等现有命令会调用）要求指定配置并通过上述检查；API 启动还会核对文件与数据库有效版本。文件、公司、环境、摘要、密钥或数据库版本不一致时拒绝启动。staging/production 强制要求部署配置，本地 development/integration 可在未固定配置包时启动。

`docker-compose.prod.yml` 及已有 GitHub staging/production 部署流程也接入相同检查，检查在迁移前执行。GitHub 部署及 1Panel install/upgrade 调用 `-migrate -apply-project-config`：迁移后校验并应用配置包对应的数据库草稿，再核对部署绑定，退出后启动服务。两个环境分别设置自己的 `RHD_PROJECT_ENVIRONMENT` 和部署配置目录，不能共用一份不同环境的配置；GitHub 回滚的新 SSH 会话同样显式指定原环境。

手动部署时，在已设置上述 `RHD_PROJECT_*` 环境变量并挂载配置及密钥的环境执行 `./remotehelpdesk -config config/config.yaml -migrate -apply-project-config`。此命令是明确的数据库写入操作，只能应用已存储且摘要一致的草稿；重复部署同一生效版本不会重复记录，过期草稿或旧生效版本不能覆盖新版本。恢复历史配置必须基于当前版本另存新草稿再部署。

普通启动与单独 `-migrate` 仍只核对部署绑定，不擅自应用文件。生产页面不能提前应用配置，所以日常保存/检查/导出草稿不会让意外重启因版本变化而失败。部署过程中替换配置文件、摘要并执行应用命令应纳入同一受控发布窗口；失败时保留与数据库当前生效版本匹配的配置包。镜像回滚不会自动回滚配置或数据库。首次初始化、真实生产部署及第三方账号联调本次均未执行。
