# SLA-001 双工单时钟使用与验收手册

日期：2026-09-17。

## 一、验收目标

验证同一个工单同时存在两个时钟：

- 总处理时间（End-to-End Elapsed Clock）：从工单创建开始，所有时间都计算。
- 责任处理时间（DayPop Accountable Clock）：等待外部供应商的时间不计入。

供应商等待期间：

```text
总处理时间：继续增长
供应商等待：持续增长
责任处理时间：暂停
```

供应商协作结束后：

```text
总处理时间：继续增长
供应商等待：停止增长
责任处理时间：继续增长
原 SLA 截止时间：顺延实际供应商等待时长
```

## 二、测试入口

- 企业工单中心：`http://localhost:3000/enterprise/tickets`
- 处理工作台：`http://localhost:3000/enterprise/ticket-workbench`
- 供应商门户：`http://localhost:3000/partner/tickets`

建议使用当前本地租户 `14`。

## 三、测试前准备

确认以下条件：

1. 技术维护组已启用。
2. `zs` 或 `tsy` 是技术维护组成员，并且当前可接单。
3. 测试工程师账号可以进入处理工作台。
4. 至少有一个有效供应商，例如 `Onward_Rag`。
5. 该供应商至少有一个启用的供应商账号。
6. 如果测试产品工单，产品模块需要绑定默认供应商；没有产品模块时可以直接选择供应商。

## 四、测试流程

### 场景 1：创建工单并接单

1. 打开企业工单中心。
2. 点击“新建工单”。
3. 填写唯一的标题，例如 `SLA-001 双时钟测试 001`。
4. 选择产品或设备，并分派给技术维护组工程师。
5. 进入处理工作台。
6. 使用被分派工程师账号点击“工程师接单”。

预期：

- 工单进入处理阶段。
- 详情页出现“工单时钟”区域。
- 刚创建时：

```text
供应商等待 = 0
责任处理时间 ≈ 总处理时间
```

### 场景 2：邀请供应商

1. 打开工单详情的“供应商协作”页签。
2. 选择需要供应商提供信息的模块或供应商。
3. 填写“需要供应商确认的问题”。
4. 设置供应商授权截止时间。
5. 点击“邀请供应商”。

预期：

- 供应商协作状态变为已邀请或处理中。
- 工单进入供应商等待状态。
- 详情页时钟显示“供应商等待中”。
- 总处理时间继续增加。
- 供应商等待时间继续增加。
- 责任处理时间停止增加。

建议记录三组值，等待 2 到 3 分钟后刷新：

| 项目 | 邀请前 | 邀请后等待 3 分钟 | 预期 |
|---|---:|---:|---|
| 总处理时间 |  |  | 增加约 3 分钟 |
| 供应商等待 |  |  | 增加约 3 分钟 |
| 责任处理时间 |  |  | 基本不变 |

### 场景 3：验证 SLA 风险口径

准备两张工单更容易验证：

#### 工单 A：暂停时剩余责任时间大于 2 小时

1. 查看工单详情中的 SLA 截止时间。
2. 在剩余责任时间大于 2 小时时邀请供应商。
3. 打开工单中心的“SLA 风险”。

预期：

- 工单仍在“处理中”。
- 暂停期间不应进入“SLA 风险”。

#### 工单 B：暂停时剩余责任时间小于或等于 2 小时

1. 选择一张距离 SLA 截止时间不足 2 小时的工单。
2. 邀请供应商，使其进入等待。
3. 打开工单中心的“SLA 风险”。

预期：

- 工单应继续出现在“SLA 风险”中。
- 等待供应商不应掩盖已经接近或超过责任期限的事实。

### 场景 4：供应商处理并结束协作

1. 登录供应商门户。
2. 进入“工单协作”或“工单”页面。
3. 找到刚邀请的协作。
4. 点击接单或接受协作。
5. 提交供应商处理结论。

注意：当前版本的等待结束点是“供应商协作结束”。供应商只发送过程消息但未结束协作时，责任时钟仍保持暂停。

预期：

- 供应商协作变为已解决。
- 详情页不再显示“供应商等待中”。
- 供应商等待时间停止增加。
- 责任处理时间恢复增长。
- SLA 截止时间顺延供应商等待的实际时长。

示例：

```text
原 SLA 截止：14:00
供应商等待：13:00 - 15:00，共 2 小时
顺延后 SLA 截止：16:00
```

### 场景 5：关闭工单

1. 工程师填写维修结论或处理结论。
2. 按工单流程完成解决、客户确认和关闭。

预期：

- 总处理时间、供应商等待和责任处理时间冻结为最终值。
- 不应存在仍在运行的供应商等待暂停。
- 关闭后的工单不再进入 SLA 风险。

## 五、可选验证项

### 多个供应商同时等待

1. 同一工单依次邀请两个不同供应商，使两个协作都处于等待状态。
2. 解决第一个供应商协作。

预期：

- 工单仍保持责任时钟暂停。

3. 解决第二个供应商协作。

预期：

- 工单此时才恢复责任时钟。
- 等待时长不会因为两个供应商重叠而重复计算。

### 供应商超时或授权过期

由于默认等待时间较长，此场景建议由开发人员缩短测试超时参数或等待后台扫描，不建议在普通验收中长时间占用。

预期：

- 协作变为超时或过期。
- 责任时钟恢复。
- 工单回到内部处理或主管兜底流程。

## 六、失败排查

### 页面没有工单时钟

1. 刷新页面。
2. 确认本地 `8083` 后端正在运行。
3. 确认数据库迁移 `148` 和 `149` 已成功执行。

### 邀请供应商后责任时钟没有暂停

检查：

- 供应商协作是否为 `invited` 或 `processing`。
- 协作是否已经被解决、超时或过期。
- 数据库 `ticket_clock_pauses` 是否存在未结束的记录。
- 工单的 `daypop_clock_paused_at` 是否为空。

### SLA 风险数量与预期不一致

检查：

- 工单是否仍然未解决。
- 暂停开始时责任 SLA 剩余时间是否大于 2 小时。
- 数据库中的 `daypop_clock_paused_remaining_seconds` 是否符合预期。
- 工单是否已经解决或关闭。

## 七、验收通过标准

满足以下全部条件即可通过：

1. 工单同时显示总处理时间、供应商等待和责任处理时间。
2. 供应商等待期间，总处理时间继续增长。
3. 供应商等待期间，责任处理时间暂停。
4. 供应商协作结束后，责任处理时间恢复。
5. SLA 截止时间按实际供应商等待时长顺延。
6. 暂停期间的工单按有效责任期限判断 SLA 风险。
7. 关闭工单后三组时间冻结，暂停状态结束。
