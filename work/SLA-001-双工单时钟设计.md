# SLA-001 双工单时钟设计

日期：2026-09-17。状态：开发完成，待用户验收。

## 需求来源

本地需求表“第4章功能对照”第 `SLA-001` 行：

> [MUST] 对每个工单同时计算 End-to-end Elapsed Clock 与 DayPop Accountable Clock。

关联约束：

- `SLA-004`：暂停原因和 DayPop Active、External Expert、Customer/Authority Pending、Planned Maintenance、Approved Hold、Stopped 等状态迁移。
- `C-07`：任何 Generic Pending 状态不得自动暂停 DayPop 责任时钟，暂停必须有批准的原因和证据。

## 简化目标

本设计先实现每个工单同时显示和计算两个时钟：

1. `End-to-end Elapsed Clock`：从工单开始到当前或结束，全部时间都计算。
2. `DayPop Accountable Clock`：从工单开始到当前或结束，只扣除已批准的外部等待时间。

第一版只把“等待外部供应商提供内容”作为可扣除区间，其他等待仍计入 DayPop Accountable Clock。

## 时钟定义

### 开始时间

优先级：

```text
received_at
→ created_at
```

第一版直接使用 `ticket.created_at`，避免历史数据缺少 `received_at` 时产生分歧。

### 结束时间

优先级：

```text
resolved_at
→ handled_at
→ 当前时间（工单仍未结束）
```

### 计算公式

```text
E2E = 结束时间 - 开始时间

DayPop Accountable =
E2E - 已批准暂停区间的并集时长
```

两个时钟默认都使用自然时间，不使用工作日历。现有 SLA 响应、接单和解决目标仍按工作日历计算，两者不要混为一个概念。

## 外部供应商等待

供应商等待区间：

```text
开始：需要供应商提供内容，工单进入供应商等待
结束：供应商提供所需内容，或供应商协作超时、过期、结束
```

MVP 的区间来源：

```text
ticket_supplier_collaborations.invited_at
→ ticket_supplier_collaborations.resolved_at
```

协作仍进行时，结束时间使用当前时间。协作超时或授权过期时，系统已有 `resolved_at`，等待区间正常闭合。

如果同一工单同时等待多个供应商，多个区间必须先合并再扣除，重叠时间只能计算一次。

## 数据模型

新增时钟暂停区间表：

```text
ticket_clock_pauses
- id
- tenant_id
- ticket_id
- reason_code
- source_type
- source_id
- started_at
- ended_at
- approved_by
- evidence_json
- created_at
- updated_at
```

第一版 `reason_code`：

```text
external_expert
```

以后实现 `SLA-004` 时增加：

```text
customer_authority_pending
planned_maintenance
approved_hold
stopped
```

约束：

- `tenant_id + ticket_id` 必须有索引。
- `source_type + source_id + reason_code` 保证事件幂等。
- 未结束暂停使用 `ended_at IS NULL`。
- 只有审核通过的暂停区间可以从 DayPop Accountable Clock 中扣除。

## SLA 分类与暂停状态的区别

暂停等待中的工单不改变原有 SLA 分类、优先级或 Service Target Profile：

```text
SLA 分类：决定 FRT、接单、解决目标和适用日历
暂停状态：决定哪些等待时间不从 DayPop Accountable Clock 中扣除
```

例如工单保持 `P1` 或原服务目标不变化，只在责任时钟上切成：

```text
DayPop Active
→ External Expert
→ DayPop Active
```

因此：

- 不要因为供应商等待把工单改成新的 SLA 优先级或新的 SLA 分类。
- 需要把供应商等待录入 SLA 领域的“暂停状态/暂停原因”，第一版原因码为 `external_expert`。
- 暂停记录必须带来源和证据，例如 `source_type=supplier_collaboration` 和 `source_id`。
- 报表按暂停原因区分时间，不能只按工单状态扣除。

这与 `SLA-004` 的要求一致：工单的状态迁移记录负责说明当前是否暂停，原有 SLA 分类负责说明应该达到什么目标，两者不能混为一个字段。

不要把该表直接合并到现有 `sla_pause_records`：

- 现有表是 SLA 通用暂停，不具备供应商来源和证据字段。
- 现有表只适合单一生效暂停，不能安全表达多个并发供应商区间。
- 直接复用会让 End-to-end Clock 也停表，违背双时钟要求。

## 自动写入规则

### 开始等待

邀请供应商成功并进入供应商协作时：

```text
reason_code = external_expert
source_type = supplier_collaboration
source_id = collaboration.id
started_at = now
ended_at = NULL
```

该操作必须与供应商协作创建处于同一数据库事务。

### 结束等待

以下任一事件发生时关闭尚未结束的供应商暂停区间：

- 供应商提交处理结论。
- 供应商协作超时。
- 供应商授权过期。
- 工单关闭时仍存在未结束的供应商协作。

MVP 以供应商协作结束作为等待结束点。后续如果业务要求“供应商第一次发送有效内容”即结束等待，再增加 `supplier_responded_at`，不改变时钟计算模型。

### 不自动暂停

以下状态不得自动暂停：

- Generic Pending。
- 工程师迟迟不处理。
- 内部转派。
- 普通客户等待，除非后续明确纳入批准的暂停原因。

## 计算服务

新增 `TicketClockService`：

```go
type TicketClockResult struct {
    E2EStartAt              time.Time
    E2EEndAt                time.Time
    E2ESeconds              int64
    PausedSeconds           int64
    AccountableSeconds      int64
    ExternalWaitSeconds     int64
    PauseActive             bool
}
```

计算步骤：

1. 取得工单开始时间和结束时间。
2. 查询该工单所有已批准暂停区间。
3. 将所有区间裁剪到工单有效时间范围内。
4. 合并重叠区间。
5. 计算暂停总时长。
6. 输出 E2E、暂停时长和 DayPop Accountable 三个值。

列表和报表不能逐张工单查询。应一次按 `ticket_id IN (...)` 读取暂停区间，再批量计算。

## API

工单聚合接口增加：

```json
{
  "clocks": {
    "e2e_start_at": "2026-09-17T09:00:00+08:00",
    "e2e_end_at": "2026-09-17T17:00:00+08:00",
    "e2e_seconds": 28800,
    "paused_seconds": 10800,
    "accountable_seconds": 18000,
    "external_wait_seconds": 10800,
    "pause_active": false
  }
}
```

规则：

- 未结束工单的 `e2e_end_at` 可以返回当前时间或为空，并用 `running=true` 表示。
- API 返回秒数作为计算事实。
- 前端负责格式化为 `8小时`、`5小时`。
- 所有查询必须带 `tenant_id`。

## 页面展示

工单详情显示：

```text
总处理时间：8小时
供应商等待：3小时
责任处理时间：5小时
```

供应商等待进行中：

```text
总处理时间：持续计时
供应商等待：2小时，进行中
责任处理时间：已暂停
```

工单列表第一版可以不展示，详情页和报表先交付。列表展示时只显示两个主值，暂停明细放悬浮提示。

### 工单中心 SLA 风险筛选

当前工单中心的 `SLA 风险` 直接比较 `sla_due_at` 和当前时间。接入双时钟后，该筛选必须改为使用有效责任期限：

```text
有效责任期限 =
原 SLA 截止时间 + 已批准暂停时长
```

规则：

- 供应商等待中的工单仍属于“处理中”，不会因为等待而自动离开处理中列表。
- 只有责任时钟接近或超过有效责任期限时，才进入 `SLA 风险`。
- 暂停等待期间，即使自然时间已经超过原 `sla_due_at`，也不应仅因此进入 `SLA 风险`。
- 暂停原因和当前时钟状态在工单详情展示，不改变原 SLA 分类。
- 如需单独查看供应商等待，可增加“等待外部”筛选，但不能把它混入 SLA 风险计数。

## 报表口径

报表使用：

```text
e2e_elapsed_minutes
daypop_accountable_minutes
external_wait_minutes
```

报表不得直接使用 `updated_at - created_at`，因为该值无法区分供应商等待，也不能在暂停期间正确计算。

## 测试

1. 无供应商等待时，E2E 与 DayPop Accountable 相等。
2. 一个供应商等待区间，两个时钟的差值等于该区间时长。
3. 两个供应商区间重叠，重叠时间只扣一次。
4. 供应商等待进行中，E2E 增长，DayPop Accountable 暂停。
5. 供应商超时和授权过期，等待区间正确闭合。
6. Generic Pending 不产生暂停，DayPop Accountable 继续计时。
7. 工单解决、关闭和重开后，开始时间不丢失，暂停历史保留。
8. 跨租户不能读取或扣除其他租户的暂停区间。
9. 列表和报表批量计算不会产生 N+1 查询。
10. 同一供应商协作重复写入暂停事件时保持幂等。

6. 接入报表口径。

## 首版实现结果

- 新增 `ticket_clock_pauses` 暂停区间表和工单责任时钟投影字段。
- 供应商邀请自动开启 `external_expert` 暂停。
- 供应商解决、超时、授权过期及工单关闭会自动结束暂停。
- 工单聚合接口同时返回 E2E、供应商等待和责任处理时间。
- 工单中心详情和“处理工作台”显示三组时钟。
- `SLA 风险`、工作台统计和报表改用有效责任期限；暂停期间的剩余责任时间固定，不随自然时间减少。
- SQLite 测试库、迁移回填和本地 PostgreSQL 环境均已验证。
