# TKT-009 通知模板与发送记录 · 交付说明

日期：2026-09-16。状态：**开发完成，已在真实环境验证，等待用户验收**。
依据：`work/TKT-009-需求对照与待办清单.md`（在线需求表需 WPS 登录，本次未访问）。

需求一句话：通知必须用已批准的模板、按接收人语言生成、遵守敏感信息规则，并记录每次发送结果。

## 一、这次做了什么

1. **模板入库 + 批准状态**：新增 `notification_templates` 表与「管理 → 通知模板」页面。模板有 `draft / approved / retired` 三种状态，**只有 approved 的模板会被用于发送**。入口：企业端 → 管理 → 通知模板。
2. **平台基线模板默认已批准**：系统自带 45 条平台模板（`tenant_id=0`，页面标记「平台基线」，不可编辑），覆盖 10 类场景 × 站内信/邮件 × zh-CN/en-US/es-ES。服务启动时幂等补齐，**新装环境不会因为一条模板都没批准而发不出通知**。租户自己新建的同 `code` 模板优先级更高，可覆盖平台基线。
3. **按接收人语言选模板**：发送前读取接收人 `User.Locale`，先匹配同语言，再回退默认语言；同一语言下租户模板优先于平台基线。渲染发生在**通知落库前**，库里存的就是接收人语言的那份文案。
4. **强制走模板**：通知的类型没有专属模板时，自动回退到已批准的「通用通知」模板；连通用模板都不存在时**不发送原文**，而是阻断本次发送并写一条 `no_approved_template` 发送记录。
5. **敏感信息检查**：发送前扫描渲染后的标题+正文，命中身份证号、银行账号、手机号、邮箱即拦截，通知不落库，并写一条 `blocked` 发送记录，队列不再重试同一条。
6. **发送记录**：新增 `notification_delivery_attempts` 表，每次发送尝试追加一条：`sent / failed / blocked / skipped`、原因、明细、渠道、尝试序号。「管理 → 通知模板 → 发送记录」可查。
7. **补齐漏网的状态更新文案**：新增 5 个模板 code —— `ticket_created_assigned`（工单已分配）、`ticket_assigned_transferred`（已转派）、`ticket_assigned_accepted`（已接单）、`ticket_assigned_cancelled`（已取消）、`ticket_assigned_recovered`（已回收），并新增 `{{Assignee}}` 变量。此前「工单 XXX 已分配 / Conversation ticket 已分配给 tsy…」这类文案是代码里写死的，现在同样由已批准模板渲染。

## 二、界面在哪里看

- 菜单：企业端左侧「管理」分组 → **通知模板**（`/enterprise/notifications/templates`）。
- 页面两个页签：**模板**（列表、筛选、新建/编辑、预览、批准、停用、删除、初始化推荐模板）、**发送记录**（渠道/状态筛选，看每次尝试的结果与原因）。
- 「初始化推荐模板」写入的是 5 类场景 × 2 渠道 × 3 语言 = 30 条**草稿**，需要管理员批准后才会取代平台基线生效。

## 三、怎么验收（建议顺序）

1. **模板驱动**：把某个已批准模板「停用」再派单，通知回到平台基线文案；换成一份文案明显不同的模板并「批准」，再派一张工单，通知文案随之改变（实测见第四节）。
2. **按语言选模板**：让工程师把个人语言切成 English（个人资料 → 语言），再派单给他，通知标题变英文；切回中文再派一次，标题变中文。
3. **敏感信息拦截**：把某个已批准模板的正文改成含手机号（如 `13800138000`）并批准，然后建一张工单；该通知不会出现在消息中心，但「发送记录」里会多出一条 `blocked`，原因 `sensitive_rule:phone_cn`。验完把模板改回来。
4. **发送记录**：在「发送记录」页签直接看，可按渠道/状态筛选。

## 四、已经跑过的验证（真实环境，非单测）

时间：2026-09-16 17:39 重启服务后（**改动必须重启后端才生效**，本次换成了含改动的本地构建）。

- **平台基线补齐**：重启后模板总数 61 → 76，其中平台基线 45 条（含 5 个新 code × 3 语言 = 15 条），全部 `approved`。
- **模板驱动对照实验**（同一入口、同一个工程师、连做三次）：

  | 步骤 | 模板状态 | 收到通知的标题与正文 |
  | --- | --- | --- |
  | A | 仅平台基线 | `工单 TK2026091600024 已分配` / `对照A-平台基线` + `已分配给 Sam Taylor，请按当前负责人继续处理。` |
  | B | 临时新增并批准一份租户模板 | `【模板验证】工单 TK2026091600025 已分配` / `对照B-租户模板` + `租户模板命中：负责人 Sam Taylor` |
  | C | 删除该租户模板 | `工单 TK2026091600026 已分配` / `对照C-恢复基线` + `已分配给 Sam Taylor，请按当前负责人继续处理。` |

  结论：通知文案确实来自模板，改模板就改文案，删掉就回平台基线；租户模板优先于平台基线。实验后已删除临时模板，模板列表恢复 76 条、无残留。
- **按语言选模板**：工程师语言切 en-US 后派单 → 英文标题；切回 zh-CN 恢复中文。
- **敏感信息拦截**：模板正文放手机号并批准 → 通知不生成，发送记录 1 条 `blocked / sensitive_rule:phone_cn`，队列不再刷重复记录。
- **已配置的租户模板**：30 条推荐草稿中的 10 条站内信已批准（ticket_created 中/英、ticket_assigned 中/英/西、ticket_closed 中/英、sla_warning 中/英），另新建并批准 1 条 `ticket_supervisor_missing`（主管兜底提醒）。
- **单测与静态检查**：`go test ./internal/services/`、`./internal/handlers/... ./internal/migration/... ./internal/bootstrap/...`、前端 `tsc --noEmit`、`eslint` 全部通过（见第六节已知限制）。

## 五、这次没做（有意简化）

模板版本历史、多级审批、退信/送达回执、可视化编辑器、多渠道（企业微信/短信）的实际投递——需求只要求“已批准 + 按语言 + 敏感信息 + 发送记录”，这些都超出范围。

## 六、已知限制

- 发送记录里 `blocked` 这条是“还没生成投递单就被拦下”，所以 `delivery_id=0`，模板 code 与命中规则写在明细里。
- 邮件/推送的 `failed`、`retry_scheduled` 记录要等真正配好 SMTP 凭据并触发邮件类通知（SLA 预警、设备紧急告警）才会出现；本地当前没有可用邮箱密码，本次只验证了站内信链路。
- 站内信发送成功不会逐条写 `sent` 发送记录（站内信直接落库+推送），发送记录目前主要在“被拦截/被拒绝/外发渠道”这些场景产生。
- 平台基线模板（`tenant_id=0`）在页面上不可编辑；要定制就新建同 code 的租户模板并批准。
