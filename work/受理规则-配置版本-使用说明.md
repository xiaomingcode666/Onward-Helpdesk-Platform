# 配置版本 使用说明（受理规则已移除）

> **2026-09-17 变更（用户要求）**：受理规则功能已前后端整体删除——配置里的 `intake` 规则、规则校验、资料齐全度评估（`context_status` / `missing_context`）、工单详情的「补充受理资料」入口、以及 `/ticket-settings/intake`、`/tickets/:id/intake` 三个接口都已移除。弹窗标题从「受理规则 · 配置版本」改为「运营配置 · 配置版本」，工具提示改为「运营配置」。
>
> **保留下来的**：来源记录去重（同一条来源记录不能重复建单）、来电/来信人资料快照（`caller_name` / `caller_phone` / `received_at`）、工单上的服务项目与工单类型、以及运营配置版本管理本身。下面第二节之后的内容只对当时那版受理规则有效，仅作历史留档。

适用页面：企业端「工单」页右上角的配置按钮，弹窗标题为 **运营配置 · 配置版本**。
说明基准：2026-09-17 之前的代码行为（配置文档 schema v1 / v2），其中受理规则部分已删除。

## 一、这个弹窗到底在管什么

弹窗同时管两件事，先分开看就不会乱：

| 部分 | 作用 | 什么时候生效 |
|---|---|---|
| 受理规则 | 规定「哪种工单必须带上哪些资料」 | 应用后，新工单才按新规则检查 |
| 配置版本 | 每次修改先存草稿，检查通过再应用；应用后生成新版本号 | 只有「应用」这一步会改变线上规则 |

如果弹窗里出现 **载入现有运营设置（升级配置）**，说明这家公司还没有把运营设置纳入版本管理（还是旧版配置）。点它之后会把渠道开关、时限、邮件等现有设置读进来变成一份未保存的草稿，核对无误后再保存、检查、应用。

## 二、先记住四个名词

| 名词 | 含义 | 举例 |
|---|---|---|
| 服务项目（不是产品） | 你们的业务分类，工单会记录它的 key | 设备售后、备件咨询、软件支持 |
| 受理渠道 | 工单从哪个入口进来 | 电话、邮件、监控告警、接口、事件推送、WhatsApp、机器人转人工 |
| 工单类型 | 该渠道下的具体业务类型，由你们自己定义 | 设备无法启动、咨询报价、换机申请 |
| 必填资料 | 这条规则要求工单必须带的字段 | 来电号码、客户、产品、设备、服务区域、来电人 |

一个服务项目可以有多个渠道、多个工单类型，每种组合一条规则。

---

## 三、规则命中条件（最关键的一条）

**服务项目 + 受理渠道 + 工单类型，三者必须完全一致，才算命中一条规则。**

命中后系统只做一件事：按这条规则检查必填资料。缺什么，工单上就标「上下文待补全」，并列出缺哪几项；**不会阻止建单**，只是提示不完整。

不命中时，工单会标一条「已确认的项目规则」缺失。典型情况：

- 该渠道没有配规则；
- 项目或工单类型为空；
- 后台「人工登记」建单：它的渠道是 `enterprise`，而受理规则只支持下面 7 种渠道，所以**永远命不中规则**。

规则支持 7 种渠道：电话受理、邮件入站、监控告警、接口、事件推送、WhatsApp、机器人转人工。

## 四、从零开始，完整操作步骤

1. 打开弹窗，先看顶部：`当前公司 #14 · 开发环境 · 当前生效：V2`。V2 是当前生效的配置版本号。
2. 如果是旧版配置，先点 **载入现有运营设置（升级配置）**，把现有设置读进来。
3. 在「服务项目（不是产品）」里点 **添加服务项目**：
   - 项目标识（key）：英文或短横线，例如 `equipment`、`spare-parts`，不能重复、不能有首尾空格；
   - 项目名称：给人看的名字，例如「设备售后」。
4. 点 **添加规则**，一行一行填：
   - 适用服务项目：下拉选择刚才建的项目；
   - 受理渠道：下拉选择，例如「电话受理」；
   - 工单类型：自己填，例如「设备无法启动」；
   - 必填资料：勾选这条规则要求的字段（见下一节）。
5. 需要几条就加几行。删除规则用每行右侧的删除图标。
6. 「部署所需密钥引用」：只有配置里用到邮件、外部接入时才需要，填运维提供的 `secret://名称`，**不要填密码**。纯电话受理可以留空，这一段直接跳过。
7. 「修改说明」必填，例如：`电话咨询增加联系电话必填`。这句会记在版本历史里。
8. 点 **检查配置**：
   - 显示「配置检查通过」才可以进入下一步；
   - 不通过时，错误会按字段位置逐条列出，照着改完再检查一次。
9. 开发环境点 **应用已检查的草稿**；预发布/生产环境按钮会变成 **导出已检查的草稿**（见第七节）。
10. 应用成功后：新工单使用新版本；**已有工单不会变**。可以打开一张新工单，在详情里确认「受理规则版本」已经变成新版本号。

## 五、必填资料怎么选

可勾选的字段和含义（**知识服务场景没有产品/设备概念，只显示前 4 项；设备售后场景才显示全部 6 项**）：

| 字段 | 含义 | 建议 |
|---|---|---|
| 来电人 `caller_name` | 打电话的人姓名 | 电话受理建议勾 |
| 来电号码 `caller_phone` | 回拨电话 | 电话受理强烈建议勾 |
| 客户 `customer_id` | 已登记客户 | 需要关联客户档案时勾 |
| 产品 `product_id` | 产品/产品线 | 售后类建议勾 |
| 设备 `device_id` | 具体设备 | 需要按设备查维修历史时勾 |
| 服务区域 `service_region` | 服务所在地 | 需要按区域派单时勾 |

勾得越多，录单越慢，但后续查询和派单越准。建议只勾真正会用到的字段。

## 六、各渠道的落地方式（照这个配）

| 渠道 | 工单怎么产生 | 除了规则还要配什么 |
|---|---|---|
| 电话受理 | 后台「新建工单」里选「电话受理」，人工录入 | 「允许的工单来源 → 人工电话受理」要勾选 |
| 邮件入站 | 邮箱收到新邮件自动建单 | 「邮件自动建单（IMAP）」启用，并设置默认服务项目和默认工单类型 |
| 监控告警 | 监控系统推送事件 | 接口/密钥由运维配置 |
| 接口 / 事件推送 / WhatsApp / 机器人转人工 | 外部系统调用接口建单 | 对应接入参数和密钥引用 |

注意两点：

- 在弹窗里加规则**不会**自动接通邮件或外部渠道；渠道要先在「允许的工单来源」里启用，并且外部账号由运维配置好。
- 规则里用到的渠道必须已在运营设置中启用，否则检查会报错。

## 七、开发 / 预发布 / 生产的差别

| 环境 | 生效方式 |
|---|---|
| 开发环境 | 页面直接「应用已检查的草稿」 |
| 预发布 / 生产，或绑定了部署配置包 | 页面禁止直接应用。保存并检查后点「导出已检查的草稿」，把导出文件交给运维，通过部署流程应用（容器内执行 `-migrate -apply-project-config`，并使用导出包里对应的配置文件和摘要）；成功后回页面点「重新加载」确认生效版本 |

部署环境这样设计，是为了避免重启后数据库配置与部署包不一致。

## 八、版本与历史怎么用

弹窗底部「历史与草稿」展开后，每个版本会标注状态：

- **当前生效**：现在在用的版本；
- **曾经生效**：曾应用过、后来被替换；
- **迁移基线**：系统启用版本管理时对老配置自动留的底；
- **未应用草稿**：保存了但还没生效。

可用操作：

- **载入为新草稿**：把某个历史版本的规则复制成一份新草稿。注意：只是复制，必须再保存、检查、应用才会生效，而且会生成**新的版本号**，旧版本不会被改写。
- **导出部署配置**：把曾经生效的版本导出成部署用的文件（只有应用过的版本才有）。
- **查看这版规则 / 查看运营设置快照**：只看不改。
- **加载更早版本**：历史较多时分页加载。

版本号是「公司 + 环境」范围内的配置版本 ID，其他配置改动也会占号，所以出现 V2 → V12 这种跳号是正常的。

## 九、权限

| 操作 | 需要的权限 |
|---|---|
| 打开这个弹窗并查看受理规则 / 版本历史 | `ticket.update` |
| 保存草稿、检查配置、应用、导出 | `ticket.update`，并且是公司所有者/管理员或拥有 `tenant.update` |

注意：配置接口统一要求 `ticket.update`。普通工程师、坐席或只读账号在页面上**看不到这个配置按钮**，不是打开后只读。

## 十、常见报错与处理

| 提示 | 原因 | 处理 |
|---|---|---|
| 请先登记这条规则所属的服务项目 | 规则里选的项目被删了或没建 | 先建服务项目，或在规则里重新选择 |
| 同一项目、渠道和工单类型只能配置一条规则 | 重复添加了同样的组合 | 删掉重复的那条，或改成不同的工单类型 |
| 受理规则使用的渠道必须明确启用 | 规则用了没启用的渠道 | 到「允许的工单来源」勾选该渠道 |
| 密钥不存在 / 不可读取 | 密钥引用写错或运维还没放密钥文件 | 核对 `secret://` 名称，联系运维补文件；纯电话受理请把密钥引用清空 |
| 当前公司及环境下的密钥不存在 | 环境不匹配（例如开发环境填了生产的密钥名） | 使用当前环境对应的密钥名 |
| 草稿保存成功但按钮是灰的 | 还没点「检查配置」，或检查没通过 | 先检查，看到「配置检查通过」再应用 |
| 应用后老工单没变化 | 这是设计如此 | 只有新工单用新版本；历史工单保留它建单时绑定的版本 |
| 新工单显示「上下文待补全：已确认的项目规则」 | 该工单没命中任何规则（常见于后台「人工登记」） | 用对应渠道建单，或补全项目、工单类型 |

## 十一、建议的最小配置（先这样跑起来）

如果只是想先让电话受理规范起来，只做三步：

1. 建一个服务项目，例如 `support` / 「售后支持」；
2. 加一条规则：`support` + 电话受理 + `咨询`，必填勾「来电人、来电号码」；
3. 检查 → 应用。

其它渠道和字段等有明确需要再逐步加，规则是累积的，不需要一次配全。

## 十二、发布前检查清单

- [ ] 服务项目标识不重复、无首尾空格；
- [ ] 每条规则的「项目 + 渠道 + 工单类型」没有重复；
- [ ] 规则用到的渠道都已在「允许的工单来源」启用；
- [ ] 需要邮件的，IMAP/SMTP 已配好并填了正确的密钥引用；
- [ ] 「检查配置」显示通过；
- [ ] 「修改说明」写清楚改了什么；
- [ ] 开发环境已应用；预发布/生产已导出并交给运维；
- [ ] 新工单详情里的「受理规则版本」已变成新版本号。
